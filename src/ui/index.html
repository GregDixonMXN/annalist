Getting started

with a record.

Use the tools you already trust. Annalist records observed file changes around them.

Choose what to record

Run annalist init in your project. Review exclusions before the first recording.

File contents and command arguments can contain secrets. There is no automatic redaction or encryption. Baseline contents of eligible project files are stored—even when a run does not modify them.

Common secret filenames are excluded by default, but arbitrary secrets are not detected. Add project-relative patterns in .annalist/config.toml. Git ignore rules are not automatically applied.

[ignore]
patterns = ["private/**", "*.log", "credentials.json"]

Wrap your coding command

annalist run -- codex

Or use any command: annalist run -- npm test. Your terminal input and output stay attached to the command; they are not captured as a transcript.

Review, then recover

Refresh run history to inspect changes and before/after file versions. Preview recovery before applying it.

annalist sessions
annalist inspect <id>
annalist rewind <id> --dry-run

Know the boundaries

Two-second polling can miss short-lived changes. Files over 10 MiB have no stored contents. Symlink contents, permissions history, empty directories, process trees, and changes outside the project are not recoverable. The wrapped command can still access the network: Annalist is a recorder, not a sandbox.

History metadata lives in your user data directory; file snapshots and pre-recovery copies live inside the project’s .annalist directory. Protect and back up both. Never commit .annalist.
